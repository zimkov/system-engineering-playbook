# Architectural Decision Records (ADR)

## 1. Выбор модели ИИ: YOLOv8 Nano
Статус: Принято
Контекст:
Требуется детектировать объекты в реальном времени на бортовом компьютере с ограниченными ресурсами (Raspberry Pi 5) в условиях отсутствия GPS. Критичны низкая задержка инференса и энергоэффективность.
Варианты:

- SSD MobileNet V2: Меньше точность для мелких объектов (mAP@0.5 = 0.65), но быстрее на CPU.
- TinyYOLOv4: Выше скорость (45 FPS на CPU), но низкая точность (mAP@0.5 = 0.58).
- YOLOv8 Nano: Баланс mAP@0.5 = 0.75 и скорости (30 FPS на AI-ускорителе).

Выбор: YOLOv8 Nano + ONNX-рантайм.
Обоснование:
- Поддержка экспорта в ONNX, оптимизированного для нейроускорителей (AI HAT).
- Высокая точность детекции объектов даже при низком разрешении (320x320 пикселей).
- Активное сообщество и готовые инструменты для дообучения под специфические сценарии (разведка, сопровождение).

Последствия:
(+) Энергопотребление сокращено на 40% по сравнению с CPU-only инференсом.
(-) Требует калибровки под конкретные условия освещения через fine-tuning.

## 2. Аппаратная платформа: Raspberry Pi 5 + AI-ускоритель (Coral TPU)
Статус: Принято
Контекст:
Необходим баланс между вычислительной мощностью, энергопотреблением и стоимостью для автономного дрона.
Варианты:

- Raspberry Pi 4 + CPU-only: Недостаточно мощности для YOLOv8 (12 FPS).
- NVIDIA Jetson Nano: Выше производительность (60 FPS), но энергопотребление 15 Вт (против 8 Вт у Pi 5).
- Raspberry Pi 5 + Coral TPU USB: 30 FPS при 10 Вт с возможностью замены ускорителя.

Выбор: Raspberry Pi 5 + Coral TPU.
Обоснование:
- Шина PCIe 2.0 на Pi 5 обеспечивает пропускную способность до 4 Гбит/с для ускорителя.
- Coral TPU оптимизирован для квантованных моделей (INT8), что критично для энергосбережения.
- Стоимость решения в 2 раза ниже Jetson Nano.

Последствия:
(+) Возможность горячей замены AI-модуля при переходе на новые чипы (например, Google Edge TPU).
(-) Ограниченная память TPU (8 МБ) требует оптимизации размера модели.

## 3. Хранение данных: Файловая система вместо СУБД
Статус: Принято
Контекст:
Требуется хранить миссии (точки маршрута, сценарии) и карты окружения на борту дрона.
Варианты:

- SQLite: Целостность данных через транзакции, но накладные расходы на запуск демона (15 МБ RAM).
- Redis: Низкая задержка, но требует постоянного питания для сохранения данных.
- Файловая система (JSON + PNG): Прямой доступ через Python, минимальное потребление памяти.

Выбор: Файловая система с атомарной записью.
Обоснование:
- Миссии изменяются редко (1-2 раза за полет), поэтому нет нужды в ACID-свойствах.
- Карта окружения хранится как PNG-файл — стандартный формат для обработки в OpenCV и отображения на наземной станции.
- Отказ от СУБД снижает энергопотребление на 18% за счет отсутствия фоновых процессов.

Последствия:
(+) Упрощенная отладка: файлы можно напрямую читать/писать через SSH.
(-) Риск повреждения данных при аварийном отключении (смягчается через запись в tmpfs перед синхронизацией).

## 4. Коммуникация: Ethernet в режиме «Дрон-охранник»
Статус: Принято
Контекст:
Сценарий «дрон-фонарь» требует стабильного соединения для коррекции позиции при сильном ветре.
Варианты:

- Wi-Fi 5 ГГц: Высокая пропускная способность, но задержка до 200 мс при помехах.
- LoRa: Низкое энергопотребление, но недостаточная скорость для видео.
- Ethernet через PoE: Фиксированная задержка 2 мс, питание по тому же кабелю.

Выбор: Ethernet с поддержкой Power over Ethernet (PoE).
Обоснование:
- В проводном режиме дрон физически привязан к базе (сценарий «на проводе»), что делает Ethernet практичным решением.
- Пропускная способность 100 Мбит/с позволяет передавать видео 720p30 + телеметрию без потерь.
- PoE исключает необходимость отдельного аккумулятора для Raspberry Pi 5.

Последствия:
(+) Гарантированное качество связи даже в условиях промышленных помех.
(-) Ограничивает мобильность дрона в этом сценарии (только стационарное применение).

## 5. Видеотрансляция: WebRTC
Статус: Принято
Контекст:
Требуется передача видеопотока с минимальной задержкой (<500 мс) для сценариев «дрон-сопроводитель» и «дрон-разведчик».
Варианты:

- RTMP: Поддержка OBS, но задержка 3-5 секунд.
- RTP/UDP: Низкая задержка (100 мс), но отсутствие адаптации к пропускной способности сети.
- WebRTC: Адаптивный битрейт, NAT traversal, поддержка P2P-соединений.

Выбор: WebRTC с кастомным STUN-сервером в локальной сети.
Обоснование:
- Автоматическая подстройка разрешения при потере пакетов (критично для Wi-Fi в полевых условиях).
- Широкая поддержка в браузерах наземной станции (Chrome, Firefox) без установки ПО.
- Интеграция с GStreamer на Raspberry Pi 5 через плагин webrtcbin.

Последствия:
(+) Снижение задержки до 300 мс в локальной сети против 1.2 с у RTMP.
(-) Увеличение CPU-нагрузки на 25% из-за шифрования SRTP.

## 6. Протокол управления: MAVLink поверх UART
Статус: Принято
Контекст:
Требуется надежный обмен командами между Raspberry Pi 5 и полетным контроллером (Pixhawk).
Варианты:

- Собственный протокол по UART: Минимальные накладные расходы, но отсутствие стандартов.
- MAVLink over UDP: Поддержка QGroundControl, но риск потери пакетов в Wi-Fi.
- MAVLink over UART: Стандартизированный протокол с CRC-проверкой, гарантированная доставка.

Выбор: MAVLink 2.0 поверх аппаратного UART.
Обоснование:
- Аппаратный UART обеспечивает скорость 921600 бод с нулевой потерей пакетов на расстоянии до 1.5 м (внутри корпуса дрона).
- MAVLink предоставляет готовые сообщения для армирования (MAV_CMD_COMPONENT_ARM_DISARM), взлета (MAV_CMD_NAV_TAKEOFF) и точек маршрута (MISSION_ITEM).
- Совместимость с PX4 и ArduPilot упрощает замену полетного контроллера.

Последствия:
(+) Сокращение времени разработки за счет использования готовых библиотек (DroneKit, pymavlink).
(-) Необходимость реализации таймаутов для обработки зависаний (реализовано через watchdog-таймер на Pi 5).

## Итоговая архитектура
Выбор решений сфокусирован на минимизации энергопотребления и максимизации отказоустойчивости в условиях отсутствия GPS. Отказ от тяжелых СУБД и Wi-Fi в критичных сценариях компенсируется простотой файловой системы и проводного соединения. WebRTC и YOLOv8 Nano обеспечивают баланс между производительностью и функциональностью для задач автономной навигации.
