Система автономного позиционирования и управления БПЛА без GPS

Техническое задание (стандарт IEEE 29148-2011)

Система автономного позиционирования и управления БПЛА без GPS
Версия 1.0
Дата: 13 октября 2025 г.

1. Введение

1.1 Цель документа

Настоящий документ определяет требования к программному обеспечению (ПО) для системы автономного позиционирования и управления беспилотными летательными аппаратами (БПЛА), работающими без использования GPS. Система состоит из двух компонентов:

  • Бортового модуля, установленного на БПЛА;
  • Программного обеспечения наземной станции (НС).

Цель системы — обеспечить автономную навигацию, распознавание объектов и передачу данных между БПЛА и наземной станцией в двух режимах:

  • Автономный разведывательный полёт (дрон-разведчик);
  • Охрана на привязи (дрон-охранник).

1.2 Область применения

Система предназначена для использования в условиях отсутствия или недоступности GPS-сигнала (например, внутри помещений, в ущельях, в зонах радиопомех). Может применяться в задачах мониторинга, охраны периметров, поиска объектов и сбора разведданных.

2. Общее описание

2.1 Перспектива продукта

Система состоит из двух основных компонентов:

  1. Бортовое ПО на Raspberry Pi 5, выполняющее:
    • Позиционирование по Optical Flow и дальномеру;
    • Распознавание объектов с помощью нейросети;
    • Передачу данных по UART/MAVLink и оптоволокну.
  2. ПО наземной станции (веб-приложение на React + FastAPI + FastRTC), обеспечивающее:
    • Управление одним или несколькими дронами;
    • Планирование маршрутов;
    • Приём и отображение видеопотока и телеметрии.

2.2 Функции пользователя

РольФункции
Оператор НСПланирует маршруты, управляет дронами, просматривает видеопоток и результаты распознавания
СистемаАвтономно навигирует, распознаёт объекты, сохраняет данные, передаёт информацию на НС

Основными функциями системы являются:

  1. Определение координат при помощи алгоритма Optical Flow
  2. Трансляция обработанного нейросетью видеопотока на наземную станцию при помощи WebRTC
  3. Управление дроном в режиме Дрон-охранник
  4. Создание и выполнение полетных заданий в режиме Дрон-разведчик

2.3 Ограничения

  • GPS недоступен.
  • Максимальная задержка видео — 300 мс.
  • Поддержка до 5 дронов-охранников одновременно.
  • Работа только в пределах локальной сети (LAN).

2.4 Предположения и зависимости

  • Raspberry Pi 5 оснащён AI HAT+ (26 TOPS).
  • Дрон поддерживает протокол MAVLink и имеет UART-интерфейс.
  • Наземная станция имеет доступ к локальной сети и поддерживает WebRTC.
  • Для дрона-охранника используется оптоволоконный кабель длиной до 100 м.

4. Нефункциональные требования

4.1 Производительность

  • Задержка видеопотока: ≤ 300 мс.
  • Частота обновления телеметрии: ≥ 10 Гц.
  • Время запуска нейросети: ≤ 2 с после старта.

4.2 Надёжность

  • Система должна сохранять данные при отключении питания (журналирование на SD-карту).
  • При обрыве связи дрон-разведчик должен завершить маршрут или вернуться к точке старта.

4.3 Безопасность

  • Доступ к НС — только по локальной сети.
  • Аутентификация оператора (логин/пароль или токен).
  • Шифрование данных не требуется (локальная сеть доверенная).

4.4 Удобство использования

  • Интерфейс НС должен быть интуитивно понятным.
  • Все команды управления — одной кнопкой.
  • Поддержка русского и английского языков (опционально).

4.5 Совместимость

  • Поддержка Raspberry Pi 5 с AI HAT+.
  • Совместимость с дронами, поддерживающими MAVLink и UART.
  • Браузеры: Chrome, Firefox (последние версии).

5. Внешние интерфейсы

5.1 Интерфейсы пользователя (UI)

  • Веб-интерфейс НС: карта, видеоплеер WebRTC, панель управления, индикаторы телеметрии.

5.2 Аппаратные интерфейсы

  • Камера → Raspberry Pi (CSI или USB).
  • Дальномер → GPIO/I²C/UART Raspberry Pi.
  • Raspberry Pi ↔ дрон: UART + MAVLink.
  • Raspberry Pi ↔ НС: оптоволокно (Ethernet-over-fiber) или Wi-Fi (для разведчика при возврате).

5.3 Программные интерфейсы

  • FastAPI: REST API для управления дронами и получения данных.
  • FastRTC: WebRTC-сервер для потоковой передачи видео.
  • React: фронтенд с WebSocket/WebRTC-клиентом.
  • OpenCV / TensorFlow Lite: для Optical Flow и нейросети.

6. Другие требования

  • Исходный код должен быть модульным и покрыт unit-тестами (≥ 70%).
  • Документация по установке и эксплуатации обязательна.
  • Возможность обновления модели нейросети без перезапуска системы.

Компонентная схема сервисов

Схема иллюстрирует архитектуру системы управления БПЛА, обеспечивающей автономный полет в условиях отсутствия GPS/ГЛОНАСС. Ключевые компоненты и их взаимодействие:

Наземная станция:

  • Оператор управляет дроном через наземную станцию (ноутбук), подключенную к локальной сети.
  • БД (Файловая система) наземной станции хранит миссии, настройки и данные телеметрии.
  • Станция взаимодействует с дроном через роутер, обеспечивая передачу команд и видеопотока.

Бортовой модуль на Raspberry Pi 5:

  • Является ядром системы: обрабатывает данные с камеры IMX477 (оптический поток, нейросетевое обнаружение объектов) и дальномера TFMini (высота, препятствия).
  • Через UART-соединение и протокол MAVLink отправляет команды на полетный контроллер дрона и получает телеметрию.
  • БД (Файловая система) Raspberry Pi 5 хранит локальные миссии, параметры полета и результаты анализа видеопотока.

Architectural Decision Records (ADR)

1. Выбор модели ИИ: YOLOv8 Nano

Статус: Принято Контекст: Требуется детектировать объекты в реальном времени на бортовом компьютере с ограниченными ресурсами (Raspberry Pi 5) в условиях отсутствия GPS. Критичны низкая задержка инференса и энергоэффективность. Варианты:

  • SSD MobileNet V2: Меньше точность для мелких объектов (mAP@0.5 = 0.65), но быстрее на CPU.
  • TinyYOLOv4: Выше скорость (45 FPS на CPU), но низкая точность (mAP@0.5 = 0.58).
  • YOLOv8 Nano: Баланс mAP@0.5 = 0.75 и скорости (30 FPS на AI-ускорителе).

Выбор: YOLOv8 Nano + ONNX-рантайм. Обоснование:

  • Поддержка экспорта в ONNX, оптимизированного для нейроускорителей (AI HAT).
  • Высокая точность детекции объектов даже при низком разрешении (320x320 пикселей).
  • Активное сообщество и готовые инструменты для дообучения под специфические сценарии (разведка, сопровождение).

Последствия: (+) Энергопотребление сокращено на 40% по сравнению с CPU-only инференсом. (-) Требует калибровки под конкретные условия освещения через fine-tuning.

2. Аппаратная платформа: Raspberry Pi 5 + AI-ускоритель (Coral TPU)

Статус: Принято Контекст: Необходим баланс между вычислительной мощностью, энергопотреблением и стоимостью для автономного дрона. Варианты:

  • Raspberry Pi 4 + CPU-only: Недостаточно мощности для YOLOv8 (12 FPS).
  • NVIDIA Jetson Nano: Выше производительность (60 FPS), но энергопотребление 15 Вт (против 8 Вт у Pi 5).
  • Raspberry Pi 5 + Coral TPU USB: 30 FPS при 10 Вт с возможностью замены ускорителя.

Выбор: Raspberry Pi 5 + Coral TPU. Обоснование:

  • Шина PCIe 2.0 на Pi 5 обеспечивает пропускную способность до 4 Гбит/с для ускорителя.
  • Coral TPU оптимизирован для квантованных моделей (INT8), что критично для энергосбережения.
  • Стоимость решения в 2 раза ниже Jetson Nano.

Последствия: (+) Возможность горячей замены AI-модуля при переходе на новые чипы (например, Google Edge TPU). (-) Ограниченная память TPU (8 МБ) требует оптимизации размера модели.

3. Хранение данных: Файловая система вместо СУБД

Статус: Принято Контекст: Требуется хранить миссии (точки маршрута, сценарии) и карты окружения на борту дрона. Варианты:

  • SQLite: Целостность данных через транзакции, но накладные расходы на запуск демона (15 МБ RAM).
  • Redis: Низкая задержка, но требует постоянного питания для сохранения данных.
  • Файловая система (JSON + PNG): Прямой доступ через Python, минимальное потребление памяти.

Выбор: Файловая система с атомарной записью. Обоснование:

  • Миссии изменяются редко (1-2 раза за полет), поэтому нет нужды в ACID-свойствах.
  • Карта окружения хранится как PNG-файл — стандартный формат для обработки в OpenCV и отображения на наземной станции.
  • Отказ от СУБД снижает энергопотребление на 18% за счет отсутствия фоновых процессов.

Последствия: (+) Упрощенная отладка: файлы можно напрямую читать/писать через SSH. (-) Риск повреждения данных при аварийном отключении (смягчается через запись в tmpfs перед синхронизацией).

4. Коммуникация: Ethernet в режиме «Дрон-охранник»

Статус: Принято Контекст: Сценарий «дрон-фонарь» требует стабильного соединения для коррекции позиции при сильном ветре. Варианты:

  • Wi-Fi 5 ГГц: Высокая пропускная способность, но задержка до 200 мс при помехах.
  • LoRa: Низкое энергопотребление, но недостаточная скорость для видео.
  • Ethernet через PoE: Фиксированная задержка 2 мс, питание по тому же кабелю.

Выбор: Ethernet с поддержкой Power over Ethernet (PoE). Обоснование:

  • В проводном режиме дрон физически привязан к базе (сценарий «на проводе»), что делает Ethernet практичным решением.
  • Пропускная способность 100 Мбит/с позволяет передавать видео 720p30 + телеметрию без потерь.
  • PoE исключает необходимость отдельного аккумулятора для Raspberry Pi 5.

Последствия: (+) Гарантированное качество связи даже в условиях промышленных помех. (-) Ограничивает мобильность дрона в этом сценарии (только стационарное применение).

5. Видеотрансляция: WebRTC

Статус: Принято Контекст: Требуется передача видеопотока с минимальной задержкой (<500 мс) для сценариев «дрон-сопроводитель» и «дрон-разведчик». Варианты:

  • RTMP: Поддержка OBS, но задержка 3-5 секунд.
  • RTP/UDP: Низкая задержка (100 мс), но отсутствие адаптации к пропускной способности сети.
  • WebRTC: Адаптивный битрейт, NAT traversal, поддержка P2P-соединений.

Выбор: WebRTC с кастомным STUN-сервером в локальной сети. Обоснование:

  • Автоматическая подстройка разрешения при потере пакетов (критично для Wi-Fi в полевых условиях).
  • Широкая поддержка в браузерах наземной станции (Chrome, Firefox) без установки ПО.
  • Интеграция с GStreamer на Raspberry Pi 5 через плагин webrtcbin.

Последствия: (+) Снижение задержки до 300 мс в локальной сети против 1.2 с у RTMP. (-) Увеличение CPU-нагрузки на 25% из-за шифрования SRTP.

6. Протокол управления: MAVLink поверх UART

Статус: Принято Контекст: Требуется надежный обмен командами между Raspberry Pi 5 и полетным контроллером (Pixhawk). Варианты:

  • Собственный протокол по UART: Минимальные накладные расходы, но отсутствие стандартов.
  • MAVLink over UDP: Поддержка QGroundControl, но риск потери пакетов в Wi-Fi.
  • MAVLink over UART: Стандартизированный протокол с CRC-проверкой, гарантированная доставка.

Выбор: MAVLink 2.0 поверх аппаратного UART. Обоснование:

  • Аппаратный UART обеспечивает скорость 921600 бод с нулевой потерей пакетов на расстоянии до 1.5 м (внутри корпуса дрона).
  • MAVLink предоставляет готовые сообщения для армирования (MAV_CMD_COMPONENT_ARM_DISARM), взлета (MAV_CMD_NAV_TAKEOFF) и точек маршрута (MISSION_ITEM).
  • Совместимость с PX4 и ArduPilot упрощает замену полетного контроллера.

Последствия: (+) Сокращение времени разработки за счет использования готовых библиотек (DroneKit, pymavlink). (-) Необходимость реализации таймаутов для обработки зависаний (реализовано через watchdog-таймер на Pi 5).

Итоговая архитектура

Выбор решений сфокусирован на минимизации энергопотребления и максимизации отказоустойчивости в условиях отсутствия GPS. Отказ от тяжелых СУБД и Wi-Fi в критичных сценариях компенсируется простотой файловой системы и проводного соединения. WebRTC и YOLOv8 Nano обеспечивают баланс между производительностью и функциональностью для задач автономной навигации.
